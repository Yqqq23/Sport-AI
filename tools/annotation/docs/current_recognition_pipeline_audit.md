and whether those values come from real models or mock logic.

## Executive Answer

The current `jersey-active-learning` candidate generation is based on mock data, not a real detector/OCR pipeline.

- `player_bbox`, `jersey_bbox`, `predicted_number`, `confidence`, and `track_id` are all generated in `backend/app/services/mock_recognition.py`.
- The sync and async recognition endpoints both call the same mock generator.
- No real YOLO, OCR, TrOCR, PaddleOCR, EasyOCR, CRNN, or custom checkpoint is loaded anywhere in the active `jersey-active-learning` backend recognition flow.

Sport-CV does contain real-model code, but it is not currently integrated into `jersey-active-learning` recognition.

## 2. Exact Source of Each Field

All five audited fields come from `backend/app/services/mock_recognition.py`.

### `track_id`

Generated in `generate_mock_predictions()`:

- file: `backend/app/services/mock_recognition.py:59-64`
- `track_pool = [1, 2, 3, 4, 5, 6, 7]`
- active tracks are chosen by frame index
- `track_id` is not tracked by a real tracker; it is assigned from this fixed synthetic pool

### `player_bbox`

Generated by `_player_bbox(track_id, frame_id, width, height)`:

- file: `backend/app/services/mock_recognition.py:23-30`
- based on synthetic geometry:
  - `track_id`
  - frame dimensions
  - deterministic drift by `frame_id`

This is handcrafted box generation, not detector output.

### `jersey_bbox`

Generated by `_jersey_bbox(player_bbox)`:

- file: `backend/app/services/mock_recognition.py:33-41`
- computed as a fixed inner sub-box of `player_bbox`

This is not a separate jersey detector.

### `predicted_number`

Generated by `_predicted_number(track_id, frame_index)`:

- file: `backend/app/services/mock_recognition.py:44-48`
- uses a hardcoded mapping like:
  - track 1 -> `23`
  - track 2 -> `11`
  - track 3 -> `7`
  - etc.
- includes one intentional inconsistency:
  - `if track_id == 1 and frame_index == 2: return "28"`

This is fake OCR output used to trigger temporal inconsistency logic.

### `confidence`

Generated in `generate_mock_predictions()`:

- file: `backend/app/services/mock_recognition.py:66-68`
- synthetic random confidence using `random.Random(video.id)`
- normal range roughly `0.55-0.90`
- periodic low-confidence injections roughly `0.31-0.39`

This is simulated score generation, not model confidence.

Sport-CV already has number recognition, so the minimum integration plan for `jersey-active-learning` is not “add OCR from scratch,” but:

1. replace `generate_mock_predictions()` with a real inference adapter
2. run real player detection/tracking first
3. derive or detect jersey regions per tracked player
4. crop jersey/number regions
5. call Sport-CV OCR recognizer or equivalent OCR backend
6. store:
   - real `player_bbox`
   - real `jersey_bbox`
   - OCR `predicted_number`
   - OCR/detector confidence
   - tracker `track_id`
7. keep existing candidate selection logic:
   - low confidence
   - temporal inconsistency

## Final Conclusion

`jersey-active-learning` currently does **not** use a real jersey detector, real OCR model, or Sport-CV inference pipeline for candidate generation.

It currently uses a pure mock generator:

- fake boxes
- fake numbers
- fake confidences
- fake track ids from a deterministic synthetic track pool

Sport-CV already contains the real building blocks needed for future integration:

- YOLO-based player detection/tracking
- number-class detection semantics
- jersey-number OCR via Roboflow SmolVLM2-based recognizer
- pose/tracking utilities

But none of those are connected to the active `jersey-active-learning` recognition endpoints yet.
